# RUA website

A static, searchable catalogue generated from the repository's `README.md`. Layout inspired by [Awesome Python](https://awesome-python.com/); RUA branding and implementation are original.

## Contributing

To add a resource, edit the root [README.md](../README.md); this website is generated from it. Start with [CONTRIBUTING.md](../CONTRIBUTING.md) for categories, row formats, metadata, and the short PR checklist. The sections below cover local development and maintainer operations.

## Build and preview

From the repository root:

```sh
python3 -m venv website/.venv
website/.venv/bin/pip install -r website/requirements.txt
website/.venv/bin/python website/build.py
python3 -m http.server 8000 --directory website/dist
```

The README uses HTML tables for the compact Papers, Benchmarks, and Social Demos layouts. Keep the `layout-paper`, `layout-benchmark`, `demo-gallery`, `demo-gallery-card`, `layout-meta`, and `layout-links` classes when editing these tables: the website reader uses them to recover dates, source labels, and video links. Badge image alt text supplies the link label; retain labels such as `Paper`, `Code · GitHub stars`, and `Models`.

Open http://localhost:8000. Edit the root README to update resources, then rebuild. Search, category and demo filters, Code linked filtering, demo date sorting within groups (RoboCurve / StationeryBench stays first when it matches the active filters), keyboard shortcuts, and expandable source details run entirely in the browser. No API key, database, or external JavaScript is required. With JavaScript disabled, the complete catalogue remains readable.

`website/dist` is generated and ignored by Git. Its files can be published to GitHub Pages or any static host, including under a repository subpath. Building does not publish the site.

## Check

```sh
website/.venv/bin/python -m unittest discover -s website -p 'test_*.py'
```

For external links and preview images, run `python website/check_links.py` (or use repeated `--url URL` arguments for changed destinations). HTTP errors are reported separately from access restrictions and network failures. This network check is manual; temporary third-party failures do not block site deployment.

An optional browser smoke check is available as `node website/check_browser.cjs` when Playwright and Chrome are already installed. Set `PLAYWRIGHT_PATH` if the package is outside the normal Node search path, and `PREVIEW_URL` to your running preview URL. It checks demo/code filters, date ordering, reset, anchor navigation, mobile overflow, and the no-JavaScript fallback.

## Publishing

The [public website](https://kairunwen.github.io/Awesome-Robot-Use-Agent/) is deployed by `.github/workflows/pages.yml`. Changes to the root README, logo, website source, or workflow on `main` trigger a build, validation, and deployment. It can also be run manually from **Actions → Deploy website → Run workflow**.

In repository **Settings → Pages**, the source must be **GitHub Actions**. Failed validation stops deployment, leaving the previous published version available.

## Google Analytics

GA4 property `553953217` uses web stream `15768875279` and measurement ID `G-BH0XB730MF`. The tag in `template.html` runs only on the production repository URL, sends one initial page view, and uses the canonical URL to combine query strings and anchors. Enhanced measurement is disabled in GA4; filters and hash navigation do not create additional page views. Local previews send no analytics. Run `node website/check_analytics.cjs` for the initialization check.

View traffic in the [RUA Analytics property](https://analytics.google.com/analytics/web/#/a407755889p553953217/reports/intelligenthome). The footer reads `views.json`, generated by `update_views.py` during deployment and hourly through the same Pages workflow. It contains only the aggregate `screenPageViews` for stream `15768875279` since collection began on 2026-09-13, with an update timestamp. This is page views, not unique visitors; GA processing and scheduled jobs can delay updates.

Setup: enable the Google Analytics Data API in a dedicated Google Cloud project, create a service account without Cloud project roles, and grant it **Viewer** access only to GA4 property `553953217`. Store its JSON key in this repository's Actions secret **GA_SERVICE_ACCOUNT_JSON**, then run **Deploy website**. Never put the key in source control or `website/dist`. Only trusted `main` push/manual/scheduled deployments can use the secret; this workflow does not run on pull requests.

API failures retain the last published snapshot and its original timestamp. If no previous valid snapshot exists, deployment stops rather than publishing a fabricated zero. The browser retains `—` when the snapshot cannot be loaded. For local preview, run the exporter with the secret in the environment after building, or copy the public `views.json` into `website/dist`; previews still do not send GA events.

## Paper and article previews

Papers, Articles, and Benchmarks render as reading lists with visible summaries and source links. A two-column resource panel places Data and Models above Code and Citation, on the right on desktop and below the summary on mobile. Citation opens the paper or article source; muted labels mean no link is listed in README.md. Full source notes remain expandable. `previews.json` maps source URLs to cover images. Paper covers are rendered from the first PDF page into `previews/`; article covers use official social images or an embedded demo poster. Entries without a cover display a text cover. Benchmarks retain their original overview images, environment descriptions, conference years, videos, and evaluation notes; release dates and conference years are shown separately.

`metadata.json` supplements README entries by source URL with verified release dates, authors, and paper-time institutions. The metadata line displays date first, then the first three authors and up to two institution names; full lists are available in Details & sources. Paper dates use the first arXiv submission, not the latest revision. Month-only dates stay month-only, and missing information is omitted. Institutions are checked against the paper PDF or official article, not inferred from authors' current profiles. Up to two official institution icons appear beside the title; their local assets live in `institutions/` and their original URLs are recorded as `logo_source`. When adding an entry, add verified metadata with its `source` and, when different, `date_source`; builds use this snapshot offline.

Run `website/.venv/bin/python website/refresh_previews.py` to fetch missing covers (requires Poppler's `pdftoppm`), then rebuild. Existing covers are reused; remove a manifest entry to refresh it. Normal builds use the checked-in thumbnails and do not fetch papers.

Papers and Benchmarks include a Publication row in Details & sources. `metadata.json` stores the verified venue, venue year, source URL, optional note, and check date under `publication`. Conference years refer to the conference edition, which can differ from the proceedings publication year and the first arXiv release. Acceptance is checked against publisher proceedings, official project pages, or arXiv publication comments; a submitted paper is not treated as accepted. Unconfirmed works retain an explicit preprint or online-resource status. Update the publication record when acceptance is confirmed, including project-URL aliases of the same paper. Benchmark covers use a larger column and tighter row spacing than the default list.

Code links display plain star counts fetched automatically when they enter view on each page visit. Counts come from Shields.io's JSON endpoint (normally cached for 30 minutes); builds do not fetch or store counts. Failed requests or disabled JavaScript leave an em dash rather than a fabricated zero.

Papers and Benchmarks default to **Newest**, including without JavaScript. Each section has independent **Newest**, **Most stars**, and **Most cited** controls. Star sorting loads all repositories in that section and ranks multiple repositories by their largest count; shared requests are reused. Abbreviated counts such as `1.2k` are ranked at their displayed precision. Citation sorting uses the loaded citation snapshot. Newest uses first release dates, treating a month or year as its first day. Missing values rank last and ties are stable. Search/code filters still apply; Reset restores Newest in both sections. Conference publication years do not replace release dates for sorting.

Citation counts use Google Scholar through [SerpApi](https://serpapi.com/google-scholar-api) when the server has `SERPAPI_KEY`. Set it as a GitHub Actions repository secret or a local environment variable; never put it in client code or a committed file. `update_citations.py` reuses the existing Pages workflow but refreshes citations only every eight days (at most four full rounds in 31 days). With 62 unique arXiv papers across Papers and Benchmarks, this needs at most 248 searches per four rounds before extra manual tests. Account quota is checked before querying; a round is skipped if the reported monthly or hourly allowance cannot cover it. No paid plan or automatic renewal is enabled by this script.

Paper matching uses exact arXiv links, or the exact normalized title if no conflicting arXiv ID exists. Citation-only fragments and ambiguous matches are excluded. Verified Scholar clusters are reused for subsequent queries. An indexed result without a Cited by link displays `0`; unmatched papers display `—`. Errors preserve previously verified counts and their timestamps. The browser links to the Scholar record and shows its source and last successful update on hover. Semantic Scholar counts are never relabeled as Google Scholar or combined with them.

The checked-in `citations.json` supplies local previews and first deployment; the published snapshot preserves later refreshes and the eight-day cooldown. Build first, then run `website/.venv/bin/python website/update_citations.py` to refresh locally with `SERPAPI_KEY` set, and copy `dist/citations.json` back to `website/citations.json` if retaining the new snapshot across local rebuilds. Without a key, a Google Scholar snapshot stays unchanged. Older Semantic Scholar snapshots can still use the original exact-arXiv-ID batch updater.

The first Social Demos source row is marked `data-demo-pinned="true"`. Preserve it when adding demos: the build carries this flag into its card, and both date orders keep it ahead of unpinned cards. New cards use original-post dates in UTC+8, and same-task follow-ups stay in Details. Text-only development logs remain separate notes. Posts with videos use demo cards even when their methods are unverified; preserve a visible status and source limitations instead of hiding the media in text notes.

Social Demos show one main task badge in `.layout-tasks`; its image alt text starts with `Task: `. Add other evidenced activities as `<p>Tasks: Pick &amp; place, Insertion.</p>` inside `.demo-notes`. The task selector includes both the badge and these additional tasks. Reuse existing labels; they describe activities, not successful outcomes or control methods. Task, scene, search, and code filters intersect. Reset clears them all, and RoboCurve stays first whenever it matches.

Demo scene buttons show counts after task, search, and code filters, before the scene filter, so switching scenes does not zero out the other choices. Check this interaction with `DEMO_COUNTS_ONLY=1 node website/check_browser.cjs`.

Social Demos use three-column `demo-gallery` tables in the README. The build converts their four `gallery-*` fields back into catalogue rows, preserving website cards, filters, and pinned ordering.
